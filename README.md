# BMS MVP

Биржа вакансий с ИИ-подбором: FastAPI + PostgreSQL на бэкенде, React + Redux Toolkit (RTK Query) на фронтенде, всё поднимается через Docker Compose.

## Быстрый старт

### 1. Клонировать репозиторий

```bash
git clone <ssh-или-https-ссылка-на-репозиторий>
cd bms-mvp
```

### 2. Создать `.env` в корне проекта

Файл `.env` не хранится в git (см. `.gitignore`), поэтому его нужно создать самостоятельно рядом с `docker-compose.yml`:

```env
POSTGRES_DB=bms
POSTGRES_USER=bms_user
POSTGRES_PASSWORD=bms_password

DATABASE_URL=postgresql://bms_user:bms_password@db:5432/bms
```

Это учётные данные только для локальной разработки, менять их не обязательно.

### 3. Собрать и поднять контейнеры

```bash
docker compose build
docker compose up -d
```

Поднимутся три контейнера:

| Сервис     | Контейнер      | Порт на хосте                          |
|------------|-----------------|-----------------------------------------|
| `frontend` | `bms-frontend`  | [http://localhost:3000](http://localhost:3000) |
| `backend`  | `bms-backend`   | [http://localhost:8000](http://localhost:8000) |
| `db`       | `bms-db`        | `localhost:5433` → `5432` внутри контейнера |

> Порт БД на хосте намеренно смещён на `5433`, чтобы не конфликтовать с локально установленным PostgreSQL (если он у вас уже слушает `5432`). Внутри docker-сети backend всегда обращается к `db:5432` — на это смещение не влияет.

При первом старте backend сам создаёт/дополняет таблицы (лёгкие идемпотентные миграции в `backend/app/migrate.py`, без Alembic) и наполняет базу демо-данными (14 вакансий, 6 компаний, 3 резюме) — никаких ручных шагов не нужно. Повторные запуски (`docker compose restart backend`) ничего не дублируют.

> **Первая сборка backend занимает заметно больше времени** (обычно 5–15 минут в зависимости от скорости интернета): образ включает `torch` и мультиязычную модель эмбеддингов (~470 МБ), которая скачивается один раз на этапе `docker compose build` и запекается в слой образа — на рантайм это не влияет, но `build` не запускайте параллельно с чем-то, ожидающим скорого результата. Собранный образ — около 2.9 ГБ (используется CPU-only сборка `torch`, а не GPU/CUDA — иначе образ раздувается до ~9.5 ГБ). После старта первый же запрос `GET /api/vacancies/match/{id}` в рамках жизни контейнера тоже займёт несколько секунд — модель подгружается в память процесса при первом обращении; дальнейшие запросы быстрые (< 1 сек).

Проверить, что всё поднялось:

```bash
curl http://localhost:8000/api/health   # {"status": "ok"}
curl http://localhost:3000              # HTML фронтенда
```

Swagger-документация API: [http://localhost:8000/docs](http://localhost:8000/docs)

### Полезные команды

```bash
docker compose logs -f backend      # логи бэкенда
docker compose build backend        # пересобрать один сервис после правок
docker compose down                 # остановить всё
docker compose down -v              # остановить и стереть данные БД (демо-данные пересоздадутся при следующем старте)
```

## Как работает ИИ-подбор вакансий по резюме

Кнопка **«Поиск вакансий с ИИ»** на странице Exchange дёргает `GET /api/vacancies/match/{resume_id}` (`backend/app/routers/vacancies.py`), который вызывает `rank_vacancies_for_resume()` из `backend/app/matching.py`. Это **не LLM и не внешний ИИ-сервис** — здесь сочетание классической статистики (пересечение навыков) и локальной модели sentence-эмбеддингов для смысловой близости текста. Расчёт полностью локальный, без сетевых вызовов и внешних API-ключей.

Итоговый процент — взвешенная сумма четырёх сигналов:

| Сигнал | Вес | Что сравнивается |
|---|---|---|
| Совпадение навыков | **45%** | `resume.skills` ↔ `vacancy.required_skills` / `preferred_skills` |
| Смысловая близость текста | **30%** | эмбеддинги `resume.title + summary` ↔ `vacancy.title + description + requirements` |
| Пересечение зарплатных ожиданий | **10%** | `resume.desired_salary_*` ↔ `vacancy.salary_*` |
| Формальные совпадения | **15%** | уровень опыта, формат работы, тип занятости |

### 1. Совпадение навыков — 45%

Навыки вакансии разделены на `required_skills` (обязательные) и `preferred_skills` (будет плюсом) — это видно и в интерфейсе: на карточке вакансии и в модалке обязательные навыки показаны сплошным тегом, желательные — пунктирной рамкой. Перед сравнением оба списка (резюме и вакансии) нормализуются через словарь синонимов (`backend/app/skill_synonyms.py`: `JS`→`javascript`, `K8s`→`kubernetes`, `Postgres`→`postgresql` и т.д. — без этого «JS» в резюме и «JavaScript» в вакансии считались бы разными навыками).

Дальше считается **F1-мера** с весом обязательных навыков вдвое выше желательных:

- **recall** = взвешенное покрытие требований вакансии → `(совпало_обязательных × 2 + совпало_желательных × 1) / (всего_обязательных × 2 + всего_желательных × 1)`
- **precision** = насколько навыки кандидата *релевантны именно этой* вакансии → `|пересечение| / |навыки резюме|`
- `skill_score = 2 · recall · precision / (recall + precision)`

Двойной вес обязательных навыков решает конкретную проблему: у некоторых вакансий в желательных бывает длинный хвост тегов (20-30 технологий), и без разделения на обязательные/желательные такой хвост несправедливо топил оценку даже для кандидата, идеально закрывающего суть вакансии.

### 2. Смысловая близость текста — 30%

Раньше здесь был TF-IDF (пересечение слов с поправкой на редкость) — он проваливался, если резюме и вакансия написаны на разных языках (например, резюме на русском, а вакансия на английском), хотя по смыслу могли отлично совпадать. Сейчас заголовок + описание + требования вакансии и заголовок + summary резюме кодируются мультиязычной моделью sentence-эмбеддингов (`sentence-transformers`, модель `paraphrase-multilingual-MiniLM-L12-v2`, см. `backend/app/embeddings.py`), между векторами считается косинусное сходство. Модель обучена так, что предложения с похожим смыслом получают близкие вектора **независимо от языка** — русское и английское описание одной и той же VR/AR-вакансии окажутся близко в векторном пространстве. Эмбеддинги вакансий кэшируются в памяти процесса, поэтому холодный первый запрос после старта контейнера медленнее последующих.

Навыки в этот текст намеренно **не** включаются — их пересечение уже отдельный сигнал (см. п.1), а включение задвоило бы влияние одного и того же списка тегов на итоговую оценку.

### 3. Пересечение зарплатных ожиданий — 10%

Диапазон `desired_salary_min/max` резюме и `salary_min/max` вакансии переводятся в доллары США по фиксированному курсу (`backend/app/matching.py: CURRENCY_TO_USD`) и сравниваются:

- диапазоны пересекаются → `1.0`
- не пересекаются → оценка плавно падает пропорционально разрыву между ними
- у резюме или вакансии не указана зарплата → нейтральные `0.5` (недостаточно данных, чтобы ни наказывать, ни поощрять)

### 4. Формальные совпадения — 15%

Три равные проверки (по ⅓ каждая):

- `resume.experience_level == vacancy.experience_level`
- `vacancy.work_format` есть в `resume.desired_work_formats`
- `vacancy.employment_type` есть в `resume.desired_employment_types`

### Итоговая формула

```
итог = 0.45 × skill_score + 0.30 × text_score + 0.10 × salary_score + 0.15 × bonus_score
match_percentage = round(итог × 100)
```

Веса подобраны экспертно, а не откалиброваны на реальных данных — это честное ограничение: без реальной статистики откликов/наймов калибровка на что-то, кроме экспертной оценки, была бы фикцией.

Вакансии сортируются по убыванию `match_percentage`. Ответ также содержит `matched_skills` и `missing_skills` — какие навыки совпали, а каких кандидату не хватает, для прозрачности подбора.

Код: [`backend/app/matching.py`](backend/app/matching.py), [`backend/app/skill_synonyms.py`](backend/app/skill_synonyms.py), [`backend/app/embeddings.py`](backend/app/embeddings.py).
