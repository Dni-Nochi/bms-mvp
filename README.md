# BMS MVP

Биржа вакансий с ИИ-подбором: FastAPI + PostgreSQL на бэкенде, React + Redux Toolkit (RTK Query) на фронтенде, всё поднимается через Docker Compose.

## Быстрый старт

### 1. Клонировать репозиторий

```bash
git clone <ssh-или-https-ссылка-на-репозиторий>
cd bms-mvp
```

### 2. Создать `.env` в корне проекта

Файл `.env` не хранится в git (см. `.gitignore`), поэтому его нужно создать самостоятельно рядом с `docker-compose.yml`:

```env
POSTGRES_DB=bms
POSTGRES_USER=bms_user
POSTGRES_PASSWORD=bms_password

DATABASE_URL=postgresql://bms_user:bms_password@db:5432/bms
```

Это учётные данные только для локальной разработки, менять их не обязательно.

### 3. Собрать и поднять контейнеры

```bash
docker compose build
docker compose up -d
```

Поднимутся три контейнера:

| Сервис     | Контейнер      | Порт на хосте                          |
|------------|-----------------|-----------------------------------------|
| `frontend` | `bms-frontend`  | [http://localhost:3000](http://localhost:3000) |
| `backend`  | `bms-backend`   | [http://localhost:8000](http://localhost:8000) |
| `db`       | `bms-db`        | `localhost:5433` → `5432` внутри контейнера |

> Порт БД на хосте намеренно смещён на `5433`, чтобы не конфликтовать с локально установленным PostgreSQL (если он у вас уже слушает `5432`). Внутри docker-сети backend всегда обращается к `db:5432` — на это смещение не влияет.

При первом старте backend сам создаёт таблицы и наполняет базу демо-данными (14 вакансий, 6 компаний, 3 резюме) — никаких ручных миграций запускать не нужно. Повторные запуски (`docker compose restart backend`) ничего не дублируют.

Проверить, что всё поднялось:

```bash
curl http://localhost:8000/api/health   # {"status": "ok"}
curl http://localhost:3000              # HTML фронтенда
```

Swagger-документация API: [http://localhost:8000/docs](http://localhost:8000/docs)

### Полезные команды

```bash
docker compose logs -f backend      # логи бэкенда
docker compose build backend        # пересобрать один сервис после правок
docker compose down                 # остановить всё
docker compose down -v              # остановить и стереть данные БД (демо-данные пересоздадутся при следующем старте)
```

## Как работает ИИ-подбор вакансий по резюме

Кнопка **«Поиск вакансий с ИИ»** на странице Exchange дёргает `GET /api/vacancies/match/{resume_id}` (`backend/app/routers/vacancies.py`), который вызывает `rank_vacancies_for_resume()` из `backend/app/matching.py`. Это **не LLM и не внешний ИИ-сервис** — здесь классический статистический подход (TF-IDF + пересечение навыков), который часто и называют «AI/ML-powered search» на джоб-бордах. Расчёт полностью локальный, без сетевых вызовов и API-ключей.

Итоговый процент — взвешенная сумма трёх сигналов:

| Сигнал | Вес | Что сравнивается |
|---|---|---|
| Совпадение навыков | **50%** | `resume.skills` ↔ `vacancy.skills` |
| Смысловая близость текста | **35%** | `resume.title + summary` ↔ `vacancy.title + description + requirements` |
| Формальные совпадения | **15%** | уровень опыта, формат работы, тип занятости |

### 1. Совпадение навыков — 50%

Берутся списки навыков резюме и вакансии (без учёта регистра) и считается **F1-мера**:

- **recall** = сколько из *требуемых вакансией* навыков закрывает кандидат → `|пересечение| / |навыки вакансии|`
- **precision** = насколько навыки кандидата *релевантны именно этой* вакансии → `|пересечение| / |навыки резюме|`
- `skill_score = 2 · recall · precision / (recall + precision)`

F1 выбран вместо простого recall специально: у некоторых вакансий бывает длинный список тегов (30+ технологий), и чистый recall несправедливо топит оценку даже для сильного кандидата. F1 балансирует между «закрыл ли я требования» и «релевантны ли вообще мои навыки».

### 2. Смысловая близость текста — 35%

Заголовок + описание + требования вакансии и заголовок + summary резюме превращаются в TF-IDF векторы (`sklearn.feature_extraction.text.TfidfVectorizer`), между которыми считается косинусное сходство (`sklearn.metrics.pairwise.cosine_similarity`). Это чисто статистическое совпадение слов с поправкой на их редкость/значимость в корпусе — синонимы и смысл без общих слов не улавливаются. Навыки в этот текст намеренно **не** включаются (иначе длинный список тегов вакансии дважды влиял бы на итог — и как отдельный сигнал, и раздувая TF-IDF вектор).

### 3. Формальные совпадения — 15%

Три равные проверки (по ⅓ каждая):

- `resume.experience_level == vacancy.experience_level`
- `vacancy.work_format` есть в `resume.desired_work_formats`
- `vacancy.employment_type` есть в `resume.desired_employment_types`

### Итоговая формула

```
итог = 0.5 × skill_score + 0.35 × text_score + 0.15 × bonus_score
match_percentage = round(итог × 100)
```

Вакансии сортируются по убыванию `match_percentage`. Ответ также содержит `matched_skills` и `missing_skills` — какие навыки совпали, а каких кандидату не хватает, для прозрачности подбора.

Код: [`backend/app/matching.py`](backend/app/matching.py).
